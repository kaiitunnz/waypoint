# Repository Guidelines

## Project Structure & Module Organization
`backend/` contains the FastAPI service. Core code lives in `backend/src/waypoint/`, with API, runtime, auth, storage, and CLI modules split by concern. The `backend/src/waypoint/telemetry/` package holds the backend-neutral usage-telemetry subsystem (fact contract, ingestion, rollups, aggregation) behind the `/api/telemetry` surface and the `/telemetry` dashboard page; see [`docs/telemetry.md`](docs/telemetry.md). The `backend/src/waypoint/notifications/` package holds the backend-neutral, opt-in notification center (durable outbox, pluggable outbound channels, Telegram in v1) that pushes new inbox items and actionable session interactions off-host; backends attach a normalized `interaction` envelope to event metadata and the runtime/notification path never branches on backend id — see [`docs/telegram-notifications.md`](docs/telegram-notifications.md). The `backend/src/waypoint/usage_providers/` package holds the backend-neutral, opt-in usage-provider subsystem (provider protocol, per-type config dispatch, runtime-owned refresh service, durable snapshot store, Lumid in v1) that surfaces session-independent account usage on `/api/usage` and the home usage panel; the runtime, dashboard, API, and telemetry paths never branch on a provider id — see [`docs/usage-providers.md`](docs/usage-providers.md). The `backend/src/waypoint/pending_asks.py` module holds the backend-neutral cross-session feed of pending questions, tool approvals, and plan approvals behind `GET /api/pending-asks` and the `pending_asks` frame on `/ws/sessions`; it reads the normalized `interaction` envelope, transports, and optional plugin protocols and never branches on backend id — see [`docs/pending_asks.md`](docs/pending_asks.md). Each session record carries a `read_at` marker, moved by session presence, that clients compare with `last_event_at` to show activity not yet seen; see [`docs/session_read_marker.md`](docs/session_read_marker.md). Backend tests live in `backend/tests/`. `frontend/` contains the Next.js PWA (v1); routes live in `frontend/src/app/` (including the `telemetry/` dashboard), and shared UI in `frontend/src/components/`; `frontend/src/lib/` keeps only the v1-specific theme provider, terminal palette, and composer constants. `frontend-v2/` is the v2 Next app (see "Frontend v2 Design System") and `packages/web-core/` is `@waypoint/web-core`, the shared TypeScript both apps consume through Next `transpilePackages`; the repo root is an npm workspace over those three with one `package-lock.json`. web-core holds the shared client logic, imported per module (`@waypoint/web-core/<module>`, `/hooks/<name>`, `/session/<name>`); its `session/` modules hold the pure session logic that the session UI calls, and its `launch/` modules hold the launch-form logic both apps' launch UIs call. The Codex backend uses the `openai-codex` Python SDK from PyPI (pinned in `backend/pyproject.toml`); the Codex collaboration-mode templates it needs are vendored under `backend/src/waypoint/backends/codex/collaboration_mode_templates/` since the wheel does not ship them.

Coding-agent backends live in `backend/src/waypoint/backends/<id>/` (currently `claude_code/`, `codex/`, `opencode/`). A session is an (agent, transport) pair: the AgentPlugin (claude_code, codex, opencode) owns the protocol, discovery, normalizer, and the AgentLaunchContract, while Transports (like the native structured adapter per agent, generic tmux, or tty-tail aka claude_tty) own send, interrupt, approval, lifecycle, and flags like is_structured and supports_resume. Each package owns its plugin descriptor, transport adapter, protocol driver, event normalizer, and backend-specific helpers — there are **no** claude/codex/opencode/tmux modules at the top level of `waypoint/`. The runtime, API, scheduler, and frontend dispatch by plugin id; never add a per-backend `if` branch in those files or the transports. The contract, capability descriptor, and a full extension recipe live in [`docs/coding_agent_plugins.md`](docs/coding_agent_plugins.md). Read it before touching anything that mentions Claude, Codex, or OpenCode by name, and before adding a new backend.

## Build, Test, and Development Commands
- `cd backend && uv sync --group dev` installs backend runtime and test dependencies.
- `cd backend && uv run pre-commit install` installs the backend git hooks for `black`, `isort`, `ruff`, `codespell`, and `mypy`.
- `cd backend && uv run waypoint serve` starts the API on port `8787` by default.
- `cd backend && uv run pytest` runs the backend test suite.
- `cd backend && uv run pre-commit run --all-files` runs the backend formatting and type/lint checks on demand.
- `npm install` (repo root) installs the dependencies of `frontend/`, `frontend-v2/` and `packages/web-core/`.
- In `frontend/` and `frontend-v2/`: `npm run dev` starts the phone-accessible Next.js dev server on `0.0.0.0`, `npm run build && npm run start` runs a production-like check, and `npm run lint` runs the linter.
- `cd packages/web-core && npm run lint && npm run typecheck && npm test` checks the shared package.

## Local Stack Supervisor
`waypointctl` (installed via `uv tool install ./waypointctl` or `pipx install ./waypointctl`) is the canonical way to manage the running stack. Use it whenever the user asks to deploy, bring up, tear down, restart, or check on the app:
- Deploy / bring up: `waypointctl start`.
- Teardown: `waypointctl stop`.
- Apply code changes: `waypointctl restart [backend|frontend]` — `waypointctl restart` and `waypointctl restart backend` are allowed, but you must have explicit permission from the user for this session before running them. If the user hasn't given that permission yet, pause and ask. `waypointctl restart frontend` can be run safely when the frontend code is updated.
- Check state during testing: `waypointctl status` for health, `waypointctl logs [backend|frontend]` for output. Restart before re-testing if you have changed code since the last `start`.
Override ports or paths inline with `WAYPOINT_STACK_BACKEND_PORT`, `WAYPOINT_STACK_FRONTEND_PORT`, `WAYPOINT_STACK_CONFIG`, or `WAYPOINT_STACK_BACKEND_DATA_DIR` rather than editing config files; values may also live in `.env` at the repo root.

`WAYPOINT_STACK_FRONTEND=v1|v2` (default `v1`) picks the app the frontend port serves; `WAYPOINT_STACK_FRONTEND_PREVIEW_PORT` also runs the other app as `frontend-preview`. See [`waypointctl/README.md`](waypointctl/README.md).

When the `waypointd` daemon is running it also serves an out-of-band remote-control console for driving the stack from a phone — status, logs, lifecycle, redeploy — when a broken frontend build or backend has made the normal app unreachable. It needs `WAYPOINT_PASSWORD` and exists only in daemon mode; see [`waypointctl/README.md`](waypointctl/README.md).

`scripts/waypoint.sh` is the legacy supervisor and is slated for deprecation; prefer `waypointctl` for new work and only fall back to the script if the user explicitly asks for it.

## Distributing Coding-Agent Skills
The repo's `.agents/skills/` are auto-installed only into the personal assistant's workspace. To let *any* coding session drive Waypoint sessions through the `waypoint` CLI (`waypoint`), spawn child Waypoint sessions (`waypoint-subagents`), message other live sessions (`waypoint-comms`), orchestrate large parallel batch jobs over the blackboard (`waypoint-workqueue`), run a multi-role software-engineering organization that drives a product through its whole lifecycle (`waypoint-crew`), run one session as an autonomous product owner that drains a project's ticket board for its lifetime (`waypoint-manager`), commit safely in the shared multi-session working tree (`waypoint-worktree`), run open-ended optimization research over isolated Waypoint search sessions (`waypoint-research`), and compact a long-running session's context at a checkpoint (`waypoint-context`), install those skills into the cross-agent global skills directory (`~/.agents/skills` by default) with `scripts/install_skills.sh install` (or `waypointctl skills install`); all nine ship in the default selection. The installer symlinks by default so the skills track the repo; pass `--skill-dir` / `WAYPOINT_SKILLS_DIR` to target an agent-specific directory (e.g. `~/.claude/skills`, `~/.codex/skills`), `--skill`/`--all` to widen the selection, and `--copy` for a detached snapshot. `status` and `uninstall` round-trip it; `uninstall` only removes symlinks the installer created, never a real or copied directory.

## Coding Style & Naming Conventions
Follow the existing style in each half of the repo. Python uses 4-space indentation, type hints, top-level imports, and `snake_case` for functions/modules; keep FastAPI handlers and Pydantic models explicit. TypeScript uses 2-space indentation, strict typing, `PascalCase` for components, and `camelCase` for helpers and state. Keep comments sparse and only explain non-obvious reasoning.

## Frontend Theming (v1)
The app supports dark (default) and light themes via the `html[data-theme="light"]` attribute set by `ThemeToggle`. All CSS lives in `frontend/src/app/globals.css`, which is organized into named sections with `/* ─── Section ─── */` dividers; when a light-mode override is genuinely needed it sits immediately after the base rule it overrides.

The design language is **flat instruments, liquid-glass chrome**:
- In-flow content (panels, cards, transcript, inputs) is flat and opaque: token surfaces (`--bg-card`, `--bg-card-soft`, `--bg-input`), solid hairlines (`--line`, `--line-strong`), radii `--radius`/`--radius-sm`, no gradients, no blur, no drop shadows, no hover lifts.
- Floating chrome only (sticky composer, docks, popovers, modals, tooltips, scroll floaters) uses the glass recipe: `background: var(--glass-bg)` (or `--glass-bg-thick` — fully opaque — for sheets that carry text), `backdrop-filter: var(--glass-blur)`, `border: 1px solid var(--glass-line)`, `box-shadow: inset 0 1px 0 var(--glass-hi), var(--shadow)`, `border-radius: var(--radius-glass)`. Never put glass on in-flow content, and never float the app bar. Write `backdrop-filter` unprefixed only — the build adds vendor prefixes, and a hand-written `-webkit-` twin makes the minifier drop the unprefixed declaration entirely.
- Badges are bare mono text in the owner's hue; statuses add a `currentColor` lamp dot. Pinned cards/headers are marked with the top-right dog-ear fold (squared corner + accent triangle), not an accent rail or edge stripe.
- Pill radii (`--radius-pill`) are reserved for true circles, capsule glass floaters, and scrollbar thumbs — content chips use `--radius-sm`.

**When adding or editing styles**, keep both themes resolving from tokens:
- Derive every color from `:root` variables, using `color-mix(in srgb, var(--token) N%, transparent)` for tints — these adapt to both themes with no override block.
- Do not introduce hardcoded dark RGBA surfaces; if a per-theme override is unavoidable, place the `html[data-theme="light"] .selector { ... }` block directly below the base rule.
- After adding component styles, verify in both themes before committing.

## Frontend v2 Design System
`frontend-v2/` styling is one token sheet plus a CSS module per component: `src/styles/tokens.css` holds every colour, radius, size and layer as a custom property (dark by default, `html[data-theme="light"]` swaps the values), and `src/styles/base.css` holds the reset. A component stylesheet only consumes `var(--token)`s: no hex or rgba values, no per-theme override blocks, and tints come from `color-mix(in srgb, var(--token) N%, transparent)`. Never grow a global stylesheet.

Rules for any v2 surface:
- **Surface tiers.** Ground (`--ground`) is receding chrome (rail, tab bar, side panes), the plane (`--plane`) is content, and the attention tier (`--attention` with `--attention-line`) is only for items that need the human.
- **Brass budget.** Brass is the primary action and needs-you markers (lamp, badge, card hairline, the recommended answer), plus the logo as the brand mark. Three faint brass mixes in `tokens.css` belong to the session transcript: the user bubble tint, the route line and the run marker ring. Limit pressure is `--warn`. Active navigation, links and selection use bright text and quiet fills.
- **Field borders.** A text field is bordered with `--field-line`, a control boundary that holds 3:1 against its surface in both themes; hairlines and dividers use `--line`.
- **No edge accents.** No per-item left highlight, accent rail or edge stripe; a selected row takes a fill.
- **Glass only on floating chrome.** Floating bars, popovers and toasts use `--glass` with `--glass-blur`; sheets, modals and drawers carry text and stay opaque. In-flow content is flat: no gradients, blur or shadows. Write `backdrop-filter` unprefixed only.
- **Type.** Six sizes (`--f-page`, `--f-title`, `--f-head`, `--f-body`, `--f-meta`, `--f-code`), plus the transcript's `--f-bubble`, `--f-stamp` and `--f-diff`, and the terminal's `--f-term`; never a literal `font-size`. Serif names things, sans carries UI and prose, mono is only for machine strings (paths, hosts, ids). Body is 16px on touch, which also keeps iOS from zooming into form fields.
- **No hint text.** No shortcut chips (⌘K, ⌘↵, ⇧Tab) and no instructional placeholders; placeholders are short nouns or verbs.
- **Safe areas.** `viewport-fit=cover` plus `--safe-top/right/bottom/left`; chrome pads itself by them, and content never sits under the Dynamic Island (59px) or the home indicator (34px). Tap targets are at least 44px on touch.
- **Layout.** Input picks the chrome and width picks the layout. A pointer client (`(hover: hover) and (pointer: fine)`) gets the 64px nav rail, popovers, centred modals, hover states, compact controls and type, and ⌘K at every width. Anything else is touch: bottom tab bar, sheets, 44px targets, 16px body and the title-tap switcher. From 900px there is room for columns. Below it there is one, where a pointer client opens the session rail and side pane as drawers and a touch client gets the phone layout. Stylesheets use the input query for chrome and density and the 900px width query for layout, and combine the two for what every client but a phone shares; components read `usePointerUI`, `useMultiColumn` or `usePhoneLayout` from `src/lib/layout.ts`, over the rules in web-core's `layoutRules`. Section order is Needs you, Pinned, Live, Exited. On touch, prefer a list row that opens a sheet over a chip strip.
- **Pinned and exited.** A Pinned heading marks pinned sessions; on the home and the session rail they use the same two-line item as Live, preview line included. A list that does not group them, such as search results, shows a small pin glyph in the row meta. Exited stays muted and single-line under a heading that hides and shows the group, collapsed until first used; the choice is one remembered setting shared by the home, the session rail and the switcher.
- **Machine text.** A command, path or query sits in mono on its own line or lines, each call in its own block with a hairline between calls. A multi-line command keeps its line breaks and a long line wraps with a hanging indent. Output is a separate muted inset block below, never inline after the command, and prose does not share a line with a machine string except as inline code. A file path takes one line: the folder is cut from the left, then the middle of the file name, and hover or a touch long press shows it whole.
- **Folds expand in place.** Whatever is truncated or folded (command output, diffs, long arguments and inputs) has a "Show all N lines" / "Show less" disclosure that reveals the whole content where it is. A scroll cap is for very long output only. Commands and output fold at eight visual lines.
- **First-line alignment.** Glyphs, lamps, route markers and checkboxes align to the first line of text, never the centre of a multi-line block.
- **Actions read as actions.** "Load older", "Show more", "Retry" and the like are `ActionChip`s: an outline, an icon where it helps, hover and pressed states, and a 44px target on touch. Bare muted text is never an action, and a list row that navigates ends in a chevron, except in a list that marks the current row with a fill, such as the rail and the switcher.
- **Session screen.** `frontend-v2/src/components/session/` holds the session frame and the compact transcript (`cards/`); the pure logic is web-core's. A pointer client gets `SessionHeader` and touch gets `SessionBar`. As columns, the rail opens from 1100px wide and the side pane from 1280px unless the person chose otherwise; with both open on a narrow window the side columns shrink so the conversation keeps 330px. Drawers start closed and are not remembered. `SessionHeader` stacks its status under the title below 1000px of its own width, and below 580px shows the view switch as icons and moves Summary and Full into the overflow menu. Width rules inside the conversation column are unnamed container queries (CSS Modules renames named containers). Toggling a fold in the transcript keeps it in place and stops following the end. The transcript takes its type and shape from `--f-bubble`, `--lh-bubble`, `--f-stamp`, `--f-diff`, `--lh-diff` and `--r-bubble`. `SessionFooter` is the slot for the dock and composer. The dock holds the attention stack (`session/attention/`): the pending approvals, else the plan to approve, else the open questions (collapsed until opened), then one-line strips for the message queue and side questions. The dock and the transcript card share one answer controller per session, so a question keeps one draft. The terminal is a main-pane view, never a side-pane tab.
- **Terminal.** `frontend-v2/src/components/session/terminal/` holds the Terminal view; its socket, keys, paste and xterm wrapper are web-core's, shared with v1. It reads capabilities from the catalog's transport fields, never backend ids. As columns, the side pane folds to its toggle while it shows. A fixed grid keeps its native size, centred on a letterbox where it fits and panning where it does not. Its key bar sits in `SessionFooter` between the dock and the composer. The term bar's menu holds the pane's actions, and the composer's session tools when no chat composer shows. An interactive live-terminal pane takes messages through `composer/TerminalCompose`, which shares the chat composer's field; any other pane keeps the chat composer below it. The pane's colours are the `--term-*` tokens, chosen by the agent's own TUI theme.
- **Settings.** `/settings` is built from the section list in `components/settings/sections.tsx`: a new section is one entry, scoped to the device or the server. A per-backend server section renders one `SettingsSection` per catalog backend, with no per-backend branches. Rows use `ui/Settings`. A phone opens one section at a time from a list; every other client shows all sections on one page, with a section list beside them from 900px. An on/off device choice is stored with web-core's `useStoredFlag`.
- **Composer.** `frontend-v2/src/components/composer/` holds the composer; its send, tuning, usage and schedule logic is web-core's, shared with v1. One set of elements serves both inputs, ordered per input so the keyboard follows the layout: a pointer client gets one bordered box, touch a control row over an input row. Enter is a newline and Cmd/Ctrl+Enter sends. Completion menus stay in the tree so the field keeps focus. Menus the person opens use `ui/Flyout` (popover on pointer, sheet on touch); the send menu stays beside its button, so the click ending a long press cannot land in a sheet. Toasts clear the composer and the attention stack; an error toast stays until it is dismissed.
- **Needs you.** `/inbox` is one queue of pending asks, inbox items and board gates. `frontend-v2/src/components/needs-you/` holds its screens and web-core its logic: v1 shares the inbox list, item, block, selection, swipe, file-drop and pane-resize hooks, their payload rules and the gate labels; the queue model and the gate reads are v2's. The queue lives in the route layout and both panes stay mounted. From 900px it is a split view, the queue on the ground tier beside the item; below that the item is pushed full screen and the tab bar hides. Opening an item marks it read, so nothing opens on its own. An approval is decided outside its detail only where the ask carries what is approved, a shell command or an edited path (`decidesInline`); every other one offers Review, on the home too. A split-view row also keeps its actions to a request it can show whole (`askRow`). An ask takes one reply at a time across its surfaces (`sessions/AskLocks`). A gate with a linked inbox item is one board row that opens the item; an answered gate stays listed, muted, and is not counted.

Primitives live in `src/components/ui/` and are shown on the internal `/gallery` route (no navigation entry); check both themes on touch at 393px and with a pointer at 1440px and 600px before shipping UI. Logic that is not presentation (host grouping, recent hosts, pending-asks merging, navigation rules) lives in `packages/web-core`.

## Testing Guidelines
Backend tests use `pytest` and `pytest-asyncio`; place new tests in `backend/tests/` as `test_<feature>.py`. Backend tests never start a real `claude`, `codex`, or `opencode` process: an autouse guard in `backend/tests/conftest.py` fails any test that starts one installed on the host, and another autouse fixture stubs the runtime's live account probe (`waypoint.runtime.probe_account`). Stub any other agent-CLI call at its plugin seam; fake agent binaries written under the pytest temp dir are allowed. Add focused unit tests for reusable runtime, storage, auth, or API behavior. Before shipping backend changes, prefer running `uv run pre-commit run --all-files` so formatting, lint, spelling, and mypy stay aligned with the repo hooks. `packages/web-core/` has a vitest suite (`npm test` there) for its shared logic; new shared frontend logic lands there with a colocated `<module>.test.ts`. The apps have no automated test harness, so at minimum run `npm run lint` and a production build in each app you change.

## Commit & Pull Request Guidelines
Recent commits use short imperative subjects such as `Add terminate and delete endpoints for sessions`. Keep commits narrowly scoped and describe the behavior change, not the implementation mechanics. Agents may create commits automatically when that helps complete a task; split backend, frontend, and docs changes into separate logical commits instead of bundling unrelated work together. PRs should include a concise summary, the commands you ran, linked issues when applicable, and screenshots for frontend changes when helpful. Call out any `.env`, Tailscale, or session-runtime setup needed for reviewers. PRs are squash-merged, so the PR title must be a Conventional Commit (`feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`) — it becomes the commit on `main` and drives release-please — and every commit must carry a DCO sign-off (`git commit -s`). See [`CONTRIBUTING.md`](CONTRIBUTING.md).

## Issue Tracking
GitHub Issues are the source of truth for active bugs and feature requests. Create one leaf issue per actionable bug or feature request, and group related items with thin tracking issues that link them as checklists. Use lowercase issue-title prefixes: `bug: ...`, `feature request: ...`, and `tracking issue: ...`. Tag bug reports with the `bug` label and feature requests with the `enhancement` label. The pinned tracking issues are `tracking issue: open bugs` (<https://github.com/kaiitunnz/waypoint/issues/4>) and `tracking issue: open feature requests` (<https://github.com/kaiitunnz/waypoint/issues/5>).

## Security & Configuration Tips
Start from `backend/.env.example` and `frontend/.env.example`; never commit real secrets. Set a real `WAYPOINT_PASSWORD` locally before exposing the service beyond localhost, and prefer configuration changes through documented env vars like `WAYPOINT_HOST`, `WAYPOINT_PORT`, and `NEXT_ALLOWED_DEV_ORIGINS`.
